# Changelog

## [Unreleased]

### Added

- First Veyra Fingers release.
- Terminal screens from the Veyra canvas: the banner with the Fingers mark, the Veyra dark and light palettes for the `dark` and `light` themes, the status line (model, provider, tokens in/out, cost, cache, budget, and the Veyra account or "core only · not signed in") on its own background (`statusBarBg`) under a location line and the editor key hints, the slash menu in a "Commands" box with `ee` tags, and the first-run screen when no model is configured (sign in to Veyra, an API key for one of the first-version providers, or environment keys).
- Veyra account: `fingers login` (and `/login` without a provider, or option 1 of the first-run screen) signs in to Veyra Connect with a device code: the code shown in the terminal, the browser opened at Connect's device page, polling with `slow_down`, `expired_token` and `access_denied` handled. The sign-in is kept only in the OS keychain, never in a file. Access tokens for other Veyra apps (connect, brain, eyes) come from the refresh grant with `resource`; rotated refresh tokens are written back under a lock shared by every fingers process. `fingers whoami` and `/org` show the account, organization, tier and group (`/org switch` signs in again); `fingers logout` and `/logout` without a provider revoke the device at Connect (RFC 7009) and clear the keychain. The status line shows the signed-in account. `FINGERS_CONNECT_URL` (or `--connect`) picks another Connect, such as `https://connect.veyra.localhost`. `/login <provider>` and `/logout <provider>` keep managing provider credentials. Fingers opens and shows only a verification page on the Connect's own address, prints names and errors from Connect without terminal escapes, keeps a refresh Connect already answered when the caller stops waiting, and signs out even when another fingers process holds the lock, without that process' refresh bringing the sign-in back (also when the sign-out lands during the keychain write or cannot write its marker). A sign-in that such a sign-out overtakes is not kept: its refresh token is revoked and `fingers login` says to sign in again.
- Open core: the `ee/` folder holds Fingers ee under the Veyra Fingers Enterprise License (`ee/LICENSE`); the MIT core never imports it and runs without it. ee features switch on only when you are signed in, your organization has the Fingers app on in Veyra Connect, and its tier includes them (tier matrix in `ee/src/tier-matrix.ts`: Low token saving; Medium sub-agents, checkpoints, Brain, Eyes; High organization hooks). Connect's answer is kept with the sign-in in the keychain and counts for 72 hours offline. `/agents` (tagged `ee`) shows the locked box while sub-agents are off; the status line says `ee on` or `core only`; `fingers login`, `fingers whoami` and `/org` name the ee features that are on or why none are. Published packages ship ee as `dist/ee/` with its own `LICENSE`.
- Token saving (ee, Low tier or higher, terminal app): a repeated read of an unchanged file sends a `[from cache, read once]` note instead of the text; bash and PowerShell outputs over 60 lines reach the model as their error lines and last 20 lines with a summary naming the full output's file; the system prompt asks for `edit` instead of rewriting files with `write`. Each saving is written to the session's savings ledger. Old tool results are pruned in two stages before compaction (from half and three quarters of the compaction limit, saved as context edits, as `[pruned by token saving]` notes), and each compaction shows what it should save before it runs and what it saved after. Compaction summaries run on a cheaper model of the same provider when one fits (`modelRouting: false` turns it off), with the dollars saved in the ledger (`model_routing`). ee modules now build against ee contract version 4 (tool hooks and the savings ledger on `EeHost`; context edits and compaction lines on the tool hooks; `routeModel` and `afterRoute` for sub-task routing), through the built-in `edition` extension.
- Memory (F20): a memory provider interface in the MIT core and Brain memory in ee (Medium tier or higher). One memory per repository (the `origin` remote, without credentials): at the start of a task Fingers adds what Brain remembers for it to the system prompt as a `<memory>` section (kept in the session), the model gets `memory_recall` and `memory_remember`, and each run's outcome goes to Brain as an idempotent learning event. Memory is the signed-in organization's: after `/org switch` or a resume under another organization the kept section is not reused, and the other organization's memory is kept out of model requests; a run whose organization changes while it streams has no memory for the rest of the run, and `/login`, `/logout` and `/org switch` wait for the run to end. Best effort: a slow or refusing Brain never stops the session. `/memory` (tagged `ee`) shows the status, recalls, remembers and turns memory off or on for the repository; the status line shows `memory: Brain “<repo>”`. Managed RPC mode announces `memory_relay`: with `configure.memory.mode: relay` it sends `memory_request` records the host answers and never calls Brain itself (`notice` `memory_unavailable` once when the host cannot). ee modules now build against ee contract version 5 (`registerMemoryProvider`, `veyraApi`, `cwd` and `repository` in command contexts).
- Telemetry (F21): OpenTelemetry GenAI spans of each run in the MIT core (`invoke_agent` per run, `chat` per model call with usage, cache tokens, finish reasons and retries, `execute_tool` per tool call, `veyra.compaction`), masked so credentials never leave, payloads only with content capture. `FINGERS_OTLP_ENDPOINT` (or `FINGERS_OTLP_TRACES_ENDPOINT`, `FINGERS_OTLP_HEADERS`, `FINGERS_OTLP_CAPTURE_CONTENT`) sends them as OTLP/HTTP JSON to your own collector; without it Fingers makes no span. Eyes telemetry in ee (Medium tier or higher): the terminal app sends each run's trace to Veyra Eyes' OTLP door with the person's token, metadata only, kept per organization; `/eyes` (tagged `ee`) shows the status and the link to the last trace, `/eyes off` and `/eyes on` stop and resume it. Managed RPC mode announces `telemetry_relay`: with `configure.telemetry.mode: relay` every span becomes a `telemetry_span` record on the run's trace (`veyra.run_id`, `veyra.fingers.agent_id`, `veyra.correlation_id`), a model call's span id is the one its request carries in `traceparent`, and Fingers sends no telemetry itself. ee modules now build against ee contract version 6 (`registerTelemetryExporter`, `createOtlpExporter`, `veyraApi(...).orgCode`).
- Savings report (F17): `/savings` in the terminal app shows what the conversation saved per technique in tokens and dollars at list price (prompt caching from the providers' usage in the core; the ee token-saving rows from the savings ledger, whose token savings are now priced at the model in use), the total and how much less it cost, the spend with the task budget, tokens in and out, cache hit ratio and provider split, the Eyes trace link when Eyes is on, and what signing in changes. A run that saved something with token saving says so when it ends. The ledger is kept in the session file (`fingers.savings` custom entries), so resumed, forked and `/tree` branches keep their savings.
- Sub-agents (F18): the `agents` tool in the MIT core and the engine in ee (Medium tier or higher, terminal app). One call starts up to 8 sub-agents, each in its own git worktree (`.fingers/worktrees/<id>`) at a snapshot of the working tree, up to 4 at once, with `depends_on` queuing; each finished one's changes are merged into the working tree as a patch (kept in its worktree when they no longer apply or when it failed). Sub-agents run on a cheaper model of the same provider when the routing rule finds one, ask the parent's approvals in the terminal one at a time, and never fail the parent. Their model calls are the tool result's usage, so the status line, `/budget` (which stops them, and starts none while it is reached; `agents` calls of one answer run one after the other) and `/savings` (`<provider> (sub-tasks)`) count them. `/agents` lists them and steers or stops one. ee modules now build against ee contract version 7 (`registerSubagentEngine`).
- `/budget` in the terminal app: a cost cap for the task in the session (`/budget 5`, `/budget off`, `/budget` to see it), counted at list price like the status line's cost and shown as `budget $X left of $Y`. The model call that reaches it is the last one; a new prompt is refused until the cap is raised. Managed RPC's `limits.max_cost_usd` uses the same stop.
- Approvals in the interactive terminal: shell commands outside the allow list show the approval box (Yes / Yes, always allow / No, tell Fingers what to do instead). `approvals.commands: "never"` turns it off; `approvals.allow` adds prefixes. The built-in read-only commands are checked argument by argument (`rg --pre`, `git diff --output`, `git branch -D` and the like ask; `fd` and `tree` are not built in), the box shows long commands in full, and each decision is recorded in the session as an `approval` entry.

### Fixed

- Managed RPC mode: `configure` with provider `openai-compatible` failed with "Unknown model" for every model id, because no catalog lists such a model. Fingers now builds the model from `configure.model.model_id` and points it at the `credentials` message's `base_url` (OpenAI chat completions, models.json custom-model defaults), with no catalog or models.json entry. A request before a `base_url` arrived fails instead of going to a default endpoint.
- Default models: models.dev no longer lists Devstral Medium or Kimi K2.7 Code on Workers AI, so the `mistral` default named a model the catalog no longer has and Cloudflare Workers AI / AI Gateway had none. The defaults are now `mistral-medium-latest` and `@cf/zai-org/glm-5.3` (`workers-ai/@cf/zai-org/glm-5.3` through AI Gateway).

### Removed

- The Pi easter eggs (`/arminsayshi`, the 3D logo) and the `ArminComponent` export.
- The status line shows the session's prompt-cache hit ratio as `cache NN%` (cache reads over all prompt tokens), replacing `CHNN.N%` (latest request only).
- Saved credentials live in the OS keychain (macOS Keychain, Secret Service, Windows Credential Manager); an existing `auth.json` is moved there and deleted. `FINGERS_CREDENTIAL_STORE=file` keeps `auth.json`. Managed RPC mode never reads stored credentials.
- First-run provider list and local detection (environment keys, AWS profiles, gcloud application default credentials), and OpenAI-compatible endpoints saved with their key in the keychain.
- `fingers --mode rpc --managed`: managed RPC mode for hosts such as Veyra Hands (Fingers RPC v1): `hello`/`configure`/`credentials` handshake, `seq` and `traceparent` correlation, JSON logs on stderr, the managed path policy, approvals, MCP servers from `configure`, `usage`, `file_changed`, limits and `result` records. See [docs/rpc-managed.md](docs/rpc-managed.md).
- Managed RPC mode sends the run's trace on every model request: a child `traceparent` of the command that started the run and the run's `X-Request-Id`.
- Managed RPC mode: `configure.system_prompt` (Fingers RPC v1): the host's instructions, added verbatim to the end of Fingers' system prompt for every model request, never into a user message and never read as a file path. Logs carry only its length.
- Managed RPC mode: the `browser` built-in tool (headless Chromium over the DevTools pipe) with `configure.network` host filtering through a proxy inside Fingers, the `browser` capability and approvals of kind `network`. The Fingers image ships Chromium. When the browser cannot start, the error names its own fatal message (for example "No usable sandbox!" on Linux without user namespaces).
- Managed RPC mode treats only the credential and credential-named header values (8+ characters) as secrets and removes them from string values only, so a short header value such as `x-flag: true` no longer turns a response into invalid JSON.
